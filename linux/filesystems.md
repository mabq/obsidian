# Filesystems

A [filesystem](https://wiki.archlinux.org/title/File_systems) decides how data is organized, named, stored, and retrieved on a storage device — without one, a disk is just a flat sequence of non-sense bytes.


### Types of Filesystems

There are many different types of filesystems, each has its own advantages, disadvantages, and unique idiosyncrasies. They can be broadly categorized into:

- **Disk-based filesystems**
  Store data persistently on physical or virtual [block devices](https://wiki.archlinux.org/title/Device_file#Block_devices) (HDDs, SSDs, USB drives).
  E.g. ext4, Btrfs, XFS, NTFS, exFAT, APFS — different trade-offs between reliability, performance, feature richness and compatibility.
<br>
- **Network filesystems**
  Store data that can be accessed from another machine over a network, as if it were local.
  E.g. NFS, SMB, CIFS.
<br>
- **Pseudo filesystems**
  These don't store data on a disk, they represent dynamic, in-memory kernel state as files.
  E.g. procfs, sysfs, tmpfs, devtmpfs.
<br>
- **Special-purpose filesystems**
  Designed to solve a very specific problem — durability on spinning disks, speed on memory, cross-platform sharing, exposing live kernel state, or layering read-only and writable data.
  E.g. squashfs, overlayfs,  cgroup.

See [create a filesystem](https://wiki.archlinux.org/title/File_systems#Create_a_file_system) (Archwiki).

### The Linux VFS (Virtual Filesystem Switch/Layer)

^64c009

A kernel subsystem that abstracts filesystems into a single API.

```
+-------------------------------------------------------------+
|               User Applications (e.g., Neovim)              |
+-------------------------------------------------------------+
|      Standard System Calls (open, read, write, close)       |
+-------------------------------------------------------------+
|                   VIRTUAL FILE SYSTEM (VFS)                 | (Abstraction Layer)
+-------------------------------------------------------------+
|    Btrfs    |    Ext4     |    XFS      |    sysfs/procfs   | (Concrete Filesystems)
+-------------+-------------+-------------+-------------------+
|  SATA SSD   |  NVMe M.2   | HDD Storage |   Kernel Memory   | (Physical/Virtual Media)
+-------------------------------------------------------------+

```

The VFS defines a common set of operations (e.g. `open()`, `read()`, `write()`, `close()`, `mkdir()`, `rename()`) that every filesystem driver must implement.

Application programs and system utilities only ever talk to the VFS (never to the filesystem directly). The VFS translates those generic calls into filesystem-specific operations behind the scenes, using the driver registered for that particular filesystem type.

The VFS uses the following core data structures to do this:

- **Superblock**
  Represents an entire mounted filesystem instance (its size, block size, state).
<br>
- **Inode**
  Represents a single file or directory's metadata (permissions, owner, timestamps, size, and pointers to where the actual data blocks are) — separate from the file's name.
<br>
- **Dentry (directory entry)**
  Maps a name to an inode, and is what makes path lookups (like `/home/user/file.txt`) fast, since dentries are cached.
<br>
- **File object**
  Represents an open file from a specific process's point of view (its current read/write offset, for example).

> [!info]
> Everything in Linux can be treated as a file!

Because every filesystem driver conforms to this same interface and populates these same structures, the kernel (and every program running on it) can treat wildly different underlying storage systems identically. This also makes it possible to write a new filesystem driver without having to change every application that uses it.


### The Unified Directory Tree

Unlike Windows, which assigns each filesystem its own drive letter (`C:`, `D:`, `E:`), Linux presents everything as **one single, unified directory tree**, starting at `/` (the root).

This is how it works:

When the system is booted the Linux kernel detects hardware and creates a temporary filesystem in memory (initramfs) containing a minimal `/`, including `/dev` with the detected hardware.

Then, the filesystem in the partition containing the core OS is mounted at `/` and it becomes the root filesystem — typically ext4, XFS, or Btrfs.

Once the root filesystem is mounted, every other filesystem is mounted onto an existing directory within that tree, called a **mount-point**. For example:

> [!info]
> The content of a mount-point (if any) is shadowed by the content of the mounted filesystem.

- `/home` — might be its own ext4 or Btrfs partition, mounted separately from root (common so user data survives an OS reinstall).
- `/boot` — is often a FAT32 filesystem on a small dedicated partition containing the bootloader.
- `/proc` — is a procfs filesystem generated by the kernel in memory, exposing running process and kernel information as virtual files. 
- `/sys` — is a sysfs filesystem generated by the kernel in memory, exposing device and driver information as files.
- `/tmp` — is a tmpfs filesystem that stores files in memory for speed and automatic cleanup.
- `/dev` — is a devtmpfs filesystem exposing hardware devices as files.
- `/mnt/usb-drive` — might be a FAT32-formatted USB stick that was mounted manually.
- `/mnt/shared-data`—  could be a remote NFS share.

See [mount a filesystem](https://wiki.archlinux.org/title/File_systems#Mount_a_file_system) (Archwiki).

It is truly amazing how the VFS transparently switches the underlying filesystem drivers as you navigate/operate files accross all these different filesystems.

> [!tip]
> Identify existing filesystems with `findmnt` or `lsblk -f`.


### FAQs


#### Why do we need to mount the boot filesystem

If the UEFI firmware directly reads the GPT partition table, finds the EFI System Partition (ESP), and executes the bootloader stored inside it, why is it necessary to mount the filesystem stored in the boot partition into `/boot` (or `/boot/efi`)?

The bootloader and kernel aren't static, they need to be updated from time to time — by mounting the boot partition to `/boot` (or `/boot/efi`), the package manager can automatically drop the new kernel and bootloader files directly onto the partition that UEFI reads during the next boot.

If the boot partition wasn't mounted, your system update would write the new kernel to the main system disk inside a plain folder named `/boot` (not shadowed). When you rebooted, the UEFI firmware would still load the old kernel living on the unmounted boot partition.


#### exFAT filesystems and user permissions

 exFAT has no on-disk concept of Unix ownership or permission bits, so the kernel driver fabricates a single, uniform set of permissions for the entire filesystem at mount time, based on options you pass in. By default many distros mount it with a restrictive `umask` and `uid`/`gid` pinned to whoever mounted it, which is why it looks locked to just you.
 
To open it up to other users (like plex), mount it like this:

```sh
sudo mount -t exfat -o uid=$(id -u),gid=$(id -g),umask=0022 /dev/sdXY /mnt/<MOUNT_POINT>
```
